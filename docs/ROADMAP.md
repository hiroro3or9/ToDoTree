# ToDoTree 機能追加ロードマップ

## 前提：このアプリの独自価値はどこにあるか

Todo アプリは世の中に無数にあります。ToDoTree が他と違うのは
**「ステップ同士の依存関係を持っている」** という一点です。
ここから導ける、他のアプリには原理的に出せない価値が 2 つあります。

1. **いま着手できるものが自動で分かる** — 先行が片付いたかどうかで決まるので、
   ユーザーが優先度を手で付け直す必要がない
2. **どこを急ぐべきかが構造から分かる** — 最長経路（クリティカルパス）や、
   「これを終えると何個のステップが動き出すか」は依存関係がないと計算できない

したがって機能追加は、**この 2 つを濃くする方向を最優先**にします。
「タグが付けられる」「色が変えられる」といった横並びの機能は後回しです。

## 体験の 5 段階と、いまの摩擦

ユーザーの流れは `書き出す → 繋ぐ → 眺める → 次を選ぶ → 進める` の 5 段階です。
現状の摩擦を並べると次のようになります。

| 段階 | いまの状態 | 摩擦 |
|---|---|---|
| 書き出す | Enter で 1 個ずつ追加 | **頭の中の 20 個を吐き出すのに 20 回の往復が要る** |
| 繋ぐ | ハンドルからドラッグ | ノードが増えると狙うのが大変。キーボードで繋げない |
| 眺める | 自動整列・検索 | 50 個を超えると全体が見えない。迷子になる |
| 次を選ぶ | 「着手できる」で色分け | **着手できるものが 10 個あるとき、どれからやるかは分からない** |
| 進める | Space で完了 | 完了しても「次に何が動き出したか」が分からない |

太字の 2 つが最大の摩擦です。これが Phase 1 になります。

---

## Phase 1 — 書き出す速さと、次を選ぶ賢さ（最優先） ✅ 実装済み

### 1-1. アウトラインの一括入力 ✅

頭の中のステップを **まとめて貼り付けて一気にグラフにする**。
このアプリの用途（細かいステップがたくさん）に最も効きます。

```
要件をまとめる
  画面のラフを描く
  データ構造を決める @9/10 ~2h #設計
実装する
  画面を作る ~8h
  保存を作る
```

- インデント（スペース 2 個 / タブ）で親子
- 行頭の `-` `*` `・` は無視
- `@9/10` 期限、`~2h` / `~90m` 見積り、`#タグ`
- 同じ深さの兄弟は、ひとつ上の階層のステップにぶら下がる
- 選択中のステップの続きとして取り込む（未選択ならルートとして）

### 1-2. 「次にやること」の順位付け ✅

着手できるステップが複数あるとき、**どれから手を付けるべきかを構造から決める**。

スコアの内訳（依存関係があるからこそ計算できるもの）:

| 要素 | 意味 |
|---|---|
| クリティカルパス上か | ここが遅れると全体が遅れる |
| 期限の近さ・超過 | 素直に急ぐべき |
| 解放するステップ数 | 終えると何個が「着手できる」に変わるか＝詰まりの解消度 |
| 下流の総量 | この先にどれだけ仕事が控えているか＝早く始めるほど良い |
| 見積りの小ささ | 同点なら短いものから片付ける |

左パネルの一番上に「次にやること」を 3 件、**理由付き**で出します
（例:「最長経路の上にあり、終えると 3 つが動き出します」）。

### 1-3. クリティカルパスの強調表示 ✅

ロジックは実装済みなので、表示を繋ぐだけ。ツールバーのトグルで
最長経路のカードと線を太く色付きにします。全体のどこが背骨かが一目で分かります。

### 1-4. 期限からの逆算（最遅開始日） ✅

ゴールや途中の期限から逆算して、各ステップの
**「この日までに終わらせないと間に合わない」** を計算します。
間に合わない見込みのステップは赤く警告します。
これも依存関係と見積りがあるからできることです。

### 1-5. 完了したら「次に動き出したもの」を教える ✅

`Space` で完了した瞬間に、新しく着手できるようになったステップの名前を出します。
「終わらせると何かが動き出す」手応えが、続ける力になります。

### 1-6. 方向キーでの移動 ✅

矢印キーで隣のステップへ選択を移す（画面上の位置関係で判断）。
`Enter` での追加と組み合わせると、**マウスに触らずに書き出しきれる**ようになります。

## Phase 2 の候補 — 一週間使ったら、どこで詰まるか

Phase 1 で「書き出す」と「次を選ぶ」は通りました。
60 ステップのプロジェクトを一週間使う場面を想像して、残った摩擦を頻度の高い順に並べると
3 つの束になります。どれも意味のある方向なので、**束ごとに** 並べます。

---

### 束 A — 手触りを直接にする ✅ 実装済み

いまは「カードを選ぶ → 右のパネルで書く」という往復が、
名前を直すたびに発生します。マインドマップ的な操作感から一番遠いのがここです。

| # | 機能 | 中身 |
|---|---|---|
| A-1 | ✅ **カード上での直接編集** | `F2` / ダブルクリック / そのまま文字を打ち始めるとカード内で編集。`Enter` で確定して次のステップへ、`Esc` で取り消し |
| A-2 | ✅ **線のクリック選択・削除** | ベジェ曲線に当たり判定を付ける。選んだ線は太く、`Delete` で外す（いまは右パネルの ✕ だけ） |
| A-3 | ✅ **キーボードで繋ぐ** | ステップを選んで `Ctrl+E` → 相手を選んで `Enter` で接続。合流をマウスなしで作れる |
| A-4 | ✅ **複数選択** | `Ctrl+クリック` と矩形ドラッグ。まとめて移動・状態変更・削除。背景ドラッグはパンのままにして、矩形選択は `Alt+ドラッグ` に割り当てる |
| A-5 | ✅ **枝ごと選ぶ** | `Ctrl+Shift+↓` でそこから下流をまとめて選択。枝ごと動かす・畳む・消すの土台になる |

**効き方**: 5 ステップの時点から毎回効きます。逆に言うと、いま一番回数の多い動作が楽になります。
**弱点**: ほぼ全部が WPF の UI で、フォーカスと当たり判定が肝。実際に触らないと詰め切れない部分が多い。

---

### 束 B — 数が増えても迷わない ✅ 実装済み（B-6 を除く）

ステップが 60、100 と増えたときに効きます。このアプリは「細かいステップがたくさん」が前提なので、
遅かれ早かれ必ず要ります。

| # | 機能 | 中身 |
|---|---|---|
| B-1 | ✅ **枝の折りたたみ** | カードの隅の三角で下流を畳む。「+12」のように隠れた数を出す。DAG なので「この枝からしか辿れないステップ」だけを畳む（他から参照されているものは残す）判定が要る |
| B-2 | ✅ **フォーカスモード** | 選択したステップの上流・下流だけを残して、関係ないものを隠す。1 本の道筋に集中できる |
| B-3 | ✅ **完了した部分を畳む** | 済んだ連なりを 1 枚にまとめる。進んだぶんだけ画面が軽くなる |
| B-4 | ✅ **ミニマップ** | 右下に全体図といまの表示範囲。クリックで飛ぶ |
| B-5 | ✅ **タグで絞る・色分ける** | タグを選ぶと該当だけ浮かび上がる。タグごとに色を割り当てる |
| B-6 | 🔸 **ズームに応じた省略** | 引いたらタイトルだけにして、密度を下げる |

**効き方**: 数が増えてから。ただし増えるのは早い（一括入力があるので）。
**強み**: 「畳む対象の判定」「表示すべき集合」はどれも Core に置けるので、テストで固められます。

---

### 束 C — 外に持ち出す・先を読む ✅ 主要な 3 つは実装済み

グラフの中に閉じていた情報を、外や未来に向けて使えるようにします。

| # | 機能 | 中身 |
|---|---|---|
| C-1 | ✅ **完了予測日** | 残りの見積り合計と、これまでの消化ペースから「この調子だと ◯/◯ に終わる」。ゴールに期限があれば間に合うかどうかも。Phase 1 の逆算と対になる、前向きの予測 |
| C-2 | ✅ **Mermaid / Markdown 書き出し** | `graph LR` で吐けば GitHub や Notion にそのまま貼れる。純粋な文字列生成なので安く、確実 |
| C-3 | **今日やることへの切り出し** | 選んだステップを「今日」に入れて、全体を眺めるモードと今日に集中するモードを行き来する |
| C-4 | **完了ログとふりかえり** | 一覧は Markdown 書き出しに含めた（🔸一部）。残り件数の推移のグラフはこれから |
| C-5 | ✅ **ステップの分割** | 大きすぎるステップを選んで分割 → 子ステップに割る。細かく刻む用途に直結する |
| C-6 | **テンプレート** | よく使う手順の型を保存して、別の場所に貼る |
| C-7 | **画像として保存 / 印刷** | キャンバスを PNG に |

**効き方**: 頻度は低いが、1 回あたりの嬉しさが大きい。C-1 と C-2 は特に安く作れます。

---

### 残っているもの

- B-6 ズームに応じた表示の省略
- C-3 今日やることへの切り出し、C-4 残り件数の推移グラフ、C-6 テンプレート、C-7 画像として保存
- そして何より **一度も実行できていない**。ビルドを通して実際に触るのが次の一手。

計算の要る部分（曲線の当たり判定、折りたたみで何が隠れるか、完了予測、優先順位）は
すべて Core に置いてテストで固めてあります。残る不確かさは、ほぼ WPF の見た目と操作感です。

## この先の見立て

外の事例と技術動向を調べた結果は [RESEARCH.md](RESEARCH.md) にまとめてあります。
そこで挙げた第 1 段（長い辺のダミーノード、起動スモークテスト、ダークモード、JSON Canvas 書き出し）が、

## 判断の基準

迷ったときは次の順で選びます。

1. **依存関係があるからこそできることか？** — そうでない機能は他アプリでも足りる
2. **ステップが 100 個になっても効くか？** — このアプリは数が多いことが前提
3. **手を止めずに済むか？** — 書き出している最中に思考を中断させない
4. **ロジックを Core に置けるか？** — 置けるならテストできる。UI は薄いほど壊れにくい
