# 個別の色分けの設計

作成日: 2026-09-07  
状態: 初版実装済み（実装状況更新: 2026-09-07）  
対象: ブロックと線に、1 つずつ色を付けられるようにする

現在の配色は[全体設計](DESIGN.md)、ブロックの前提は[ブロック設計](BLOCKS_DESIGN.md)を参照。
本文は着手前の設計案で、実装は 9 節までおおむねこのとおりに入れた。
実装時に変えた点は 11 節にまとめてある。現在の操作は[README](../README.md)を参照。

## 1. 目的と優先順位

大きくなったグラフで「どの一帯が何の話か」「この依存だけは別扱い」を、
名前を読まずに見分けられるようにする。

状態色（着手可能・進行中・完了・最長経路）は現在の主役であり、
個別の色分けはその邪魔をしない。カードの状態色は変えず、
奥に敷くブロックの囲みと、状態を持たない通常の線だけを対象にする。

成功の基準は、右クリックから 2 手で色が変わり、Undo で戻り、
再起動しても残り、ライト／ダークのどちらでも読めること。

## 2. 初版の範囲

実装するもの:

- ブロック 1 つに色を 1 つ。囲みの背景・枠・見出しの下地に効く。
- 線 1 本に色を 1 つ。線と矢印の先に効く。
- プリセット 9 色＋「既定」。右クリックの色見本から選ぶ。
- 保存・復旧、Undo / Redo、タブ独立性。
- ミニマップの囲みの枠にも反映する。

次段階に回すもの:

- カード（ステップ）単体の色。状態色と衝突するため、別に設計する。
- 任意色のカラーピッカー、色の名前の変更、独自パレットの保存。
- 複数のブロック・線へのまとめて適用（現在ブロックも線も単一選択のため）。
- 色による絞り込み・検索、書き出し（Markdown / Mermaid）への反映。
- ブロックの色を所属カードへ薄く波及させる表現。

色は装飾であって、依存関係・着手可能判定・進捗・最長経路・完了予測には一切関わらない。

## 3. プリセットの色

### 3.1 選び方

- 9 色。色覚特性を踏まえ、隣り合う色相を詰め込みすぎない。
- ライトとダークで同じ id を使い、値だけ差し替える。明度は各テーマで取り直す。
- 「既定」は色を持たない状態（`null`）であり、10 番目の色ではない。

| id | 表示名 | 想定 |
|---|---|---|
| `slate` | 灰 | 既定に近いが、明示的に「色を決めた」もの |
| `red` | 赤 | 止まっている・要注意 |
| `orange` | 橙 | 急ぎ |
| `amber` | 黄 | 保留・確認待ち |
| `green` | 緑 | 順調 |
| `teal` | 青緑 | 標準（アクセント色と同系） |
| `blue` | 青 | 調査・設計 |
| `violet` | 紫 | 検討中 |
| `pink` | 桃 | 他人の担当・外部要因 |

表示名は目安であり、意味は使う人が決める。アプリ側は意味を持たせない。

### 3.2 リソースキー

既存キーの末尾に id を足すだけの規則にする。参照側は
「`<既存キー>.<id>` を引き、無ければ `<既存キー>`」の 1 本道になる。

| 用途 | 既定のキー | 色付きのキー |
|---|---|---|
| 囲みの背景 | `Block.Fill` | `Block.Fill.red` |
| 囲みの枠 | `Block.Stroke` | `Block.Stroke.red` |
| 見出しの下地 | `Block.Header.Fill` | `Block.Header.Fill.red` |
| 線と矢印 | `Edge.Normal` | `Edge.Normal.red` |

1 色あたり 4 キー、9 色で 36 キーを `Palette.Light.xaml` と `Palette.Dark.xaml`
の両方へ足す。**両方に同じキーを必ず用意する**（[CLAUDE.md](../CLAUDE.md)の約束）。

派生は増やさない。次の 2 つはキーを足さず、コード側で不透明度から作る。

- 選択中の囲みの背景 … その色の背景を少し濃くする（`Opacity` を上げる）。
- 先行が片付いた線 … その色を 45% の不透明度で描く。

## 4. 状態色との優先順位

色分けは「その要素が普段どう見えるか」だけを変える。
いま注目している・危ないという合図は、これまでどおり状態色が担う。

### 4.1 線

上から優先。個別色は最下段の 2 つにだけ効く。

| 順 | 状態 | 色 |
|---|---|---|
| 1 | 選択中 | `Edge.Selected`（個別色を無視） |
| 2 | 最長経路 | `Edge.Critical`（個別色を無視） |
| 3 | 選択ノードに繋がる | `Edge.Highlight`（個別色を無視） |
| 4 | 先行が片付いた | 個別色の 45%、無ければ `Edge.Settled` |
| 5 | 通常 | 個別色、無ければ `Edge.Normal` |

太さは現行のまま変えない。集約された線の破線も現行どおり。

畳んだブロックへ集約された線には色を付けられない（メニューを無効にして理由を出す）。
同じ経路に複数本が重なって描かれるので、1 本だけ塗っても隣に上書きされて見えないため。

### 4.2 ブロック

- 背景・枠・見出しの下地は個別色を使う。
- **選択中の枠は色に関わらず `Block.Selected.Stroke`（アクセント）のまま**。
  どの色のブロックでも「いま選んでいる」が同じ見え方になることを優先する。
- 選択中の背景は個別色を濃くしたもの。色の見分けを保ったまま選択が分かる。
- 選択中の見出しの下地は、既定色のときだけ `Block.Header.Selected.Fill`。
  色付きのときはその色の下地のままにする（選択は枠と背景で分かるため）。
- ドロップ先の強調（`IsDropTarget`）は選択と同じ扱いにする。
- 所属カードの補助輪郭（`Block.Member.Stroke`）は色分けしない。
- 囲みの四辺にある接続用の丸は、いま `HeaderFill` と `BorderBrush` をそのまま使っている。
  色を付けると丸も一緒に染まる。意図した挙動として扱い、別のキーは足さない。

## 5. 操作仕様

### 5.1 色を選ぶ

ブロックの見出しを右クリック → 「色」→ 色見本の一覧。
線を右クリック → 「色」→ 同じ一覧。

```text
  ブロックの見出しを右クリック
  ┌─────────────────────────┐
  │ ブロックを畳む / 開く      │
  │ このブロックに集中 / 解除   │
  │ ここから繋ぐ              │
  │ ─────────────────────── │
  │ 中を整列          Ctrl+L │
  │ 名前を変更           F2 │
  │ 色                    ▶ │──┬──────────────┐
  │ 中のステップを選択        │  │ ● 既定  ✓    │
  │ 部品として保存…          │  │ ────────────│
  │ ─────────────────────── │  │ ● 灰        │
  │ ブロックを解除  Ctrl+Shift+G│  │ ● 赤        │
  └─────────────────────────┘  │ ● 橙        │
                                │ …           │
                                └──────────────┘
```

- 各行は左に色の丸（`MenuItem.Icon`）、右に表示名。
- いま適用中の色に印を付ける（`IsChecked`）。
- 先頭は「既定」。選ぶと色を外す（`ColorId` を `null` に戻す）。
- 一覧は「ブロックに追加」と同じく `ItemsSource` ＋ `ItemContainerStyle` で組む。
- ブロック用と線用で別のコレクションを持ち、どちらへ効くかを取り違えないようにする。

キーボードからの色変更は初版では用意しない。

### 5.2 Undo と保存

- 色を変える直前に `PushUndo()` を呼ぶ。1 回の選択が 1 回の Undo で戻る。
- 同じ色を選び直したときは、履歴も未保存状態も増やさない。
- 変更後は `MarkDirty()` → `RefreshAll()`。
  ブロックは `RefreshBrushes()` で塗り直り、線は `EdgeLayer.Redraw()` で描き直す。
- タブごとに独立。他のタブの色は動かさない。

### 5.3 状態メッセージ

- 色を付けたとき: 「「設計」を赤にしました。」
- 既定へ戻したとき: 「「設計」の色を既定に戻しました。」
- 線のとき: 「線の色を青にしました。」（線には名前が無いため相手を呼ばない）

## 6. データモデルと保存

### 6.1 モデル

`ToDoTree.Core` に、WPF に依存しない形で持たせる。

```csharp
// Models/TodoBlock.cs
/// <summary>個別の色。null は既定色。未知の id は既定として描くが、値は捨てない。</summary>
public string? ColorId { get; set; }

// Models/TodoEdge.cs
public string? ColorId { get; set; }
```

プリセットの一覧も Core に置き、テストできるようにする。

```csharp
// Models/ColorPresets.cs
public sealed record ColorPreset(string Id, string DisplayName);

public static class ColorPresets
{
    public static IReadOnlyList<ColorPreset> All { get; } = [ /* slate … pink */ ];
    public static bool IsKnown(string? id);
}
```

`Clone()` は `MemberwiseClone` のままで文字列も複写されるため、変更は不要。
`TodoProject.DeepClone()` も既存の `Clone()` 経由でそのまま動く。

### 6.2 保存形式

`schemaVersion` を **4 → 5** に上げる。

上げる理由は、古い版のアプリが新しいファイルを読み込み時に拒むため。
`colorId` を知らない版で開いて保存すると、色だけが黙って消える。
ブロック（形式 2）としおり（形式 3）と同じ扱いにする。

```json
{
  "schemaVersion": 5,
  "blocks": [
    { "id": "…", "title": "設計", "colorId": "blue", "nodeIds": ["…"] }
  ],
  "edges": [
    { "id": "…", "fromId": "…", "toId": "…", "colorId": "red" }
  ]
}
```

- 既定色のときは `colorId` を書き出さない
  （`DefaultIgnoreCondition = WhenWritingNull` に乗るので、既存ファイルの見た目を変えない）。
- 形式 4 以前のファイルは `colorId` なしで読め、全部が既定色になる。
- **未知の id は読み込みを止めない。** 既定色で描き、値はそのまま保持して書き戻す。
  色は装飾であり、開けなくする理由にならない。所属情報の破損（読み込みごと止める）とは扱いを変える。

### 6.3 責務の分担

| 層 | 持つもの |
|---|---|
| `ToDoTree.Core` | `ColorId`、プリセットの id と表示名、保存・複写・検証 |
| `ToDoTree.App` | id → リソースキーの解決、ブラシ生成、メニュー、コマンド |

Core は色の値（RGB）を一切知らない。値は `Palette.*.xaml` にだけ置く。

### 6.4 ブラシの引き方

```csharp
// Services/ThemeManager.cs に追加
/// <summary>色 id 付きのキーを引き、無ければ既定のキーへ落ちる。</summary>
public static Brush BrushOf(string baseKey, string? colorId) =>
    colorId is null ? BrushOf(baseKey)
        : Application.Current?.TryFindResource($"{baseKey}.{colorId}") as Brush ?? BrushOf(baseKey);
```

未知の id・キーの入れ忘れ・テーマ片側だけの定義漏れが、
すべて「既定色で描く」に収束する。落ちない。

`EdgeLayer` は現在ペンを 1 組だけ持っている。色付きの線のために
`Dictionary<string, Pen>` を足し、`ThemeManager.Generation` と
`NodeMetrics.Generation` が変わったときに丸ごと捨てる（既存の作り直しの仕組みに乗せる）。
ペンは作った直後に `Freeze()` する。

## 7. 実装順

1. **Core**: `ColorId` 2 か所、`ColorPresets`、`schemaVersion` 5、テスト。
2. **パレット**: `Palette.Light.xaml` / `Palette.Dark.xaml` に 36 キーずつ追加。
3. **描画**: `ThemeManager.BrushOf(baseKey, colorId)`、`BlockViewModel` の 3 つのブラシ、
   `EdgeLayer` の色付きペンと優先順位。
4. **操作**: 右クリックの「色」サブメニュー、コマンド、Undo、状態メッセージ。
5. **仕上げ**: ミニマップの囲みの枠、[README](../README.md)・[ロードマップ](ROADMAP.md)・
   [ブロック設計](BLOCKS_DESIGN.md)（「色の個別設定」を未実装一覧から外す）の更新。

1 と 2 は独立して進められる。3 は 2 に依存する。

## 8. 受け入れ条件

- ブロックの見出しを右クリック →「色」→ 赤 で、囲みの背景・枠・見出しが赤系になる。
- 線を右クリック →「色」→ 青 で、線と矢印の先が青になる。
- 色を変えた直後の `Ctrl+Z` で 1 回で元の色に戻り、`Ctrl+Y` でやり直せる。
- 保存して開き直しても色が残る。形式 4 のファイルも開け、全部が既定色で出る。
- 色を付けたブロックを選ぶと、枠はアクセント色になり、背景は色を保ったまま濃くなる。
- 色を付けた線が最長経路・選択・強調のいずれかになったとき、状態色が優先される。
- ライトとダークを切り替えても、9 色すべてで見出しの文字と件数が読める。
- 色を付けたブロックと線がある状態で、整列・吸着・折りたたみ・集中表示が従来どおり動く。
- `colorId` に知らない値が入ったファイルを開いても、エラーにならず既定色で表示される。
- 未使用の色キーが `Palette.Light.xaml` と `Palette.Dark.xaml` で片側だけになっていない。

## 9. テスト

`ToDoTree.Core.Tests` に追加する（WPF に依存しない範囲）。

- `ColorId` が保存 → 読み込みで往復する（ブロック・線それぞれ）。
- 既定色のとき `colorId` が JSON に出ない。
- 形式 4 のファイルを読むと `ColorId` が `null` になる。
- 未知の `colorId` でも読み込みが成功し、値が保持される。
- `Clone()` / `DeepClone()` が `ColorId` を引き継ぐ。
- `ColorPresets.All` の id に重複が無く、すべて `IsKnown` が真。

パレットのキー漏れ（片側のテーマにだけ存在する）は Core のテストでは見つからない。
`Palette.Light.xaml` と `Palette.Dark.xaml` のキー集合を突き合わせる小さな検査を
別途 App 側かスクリプトで用意するか、手順として[開発・検証ガイド](DEVELOPMENT.md)に残す。

実マウスでの確認（メニューの出し分け、色見本の見やすさ、9 色の実際の印象）は
Windows 側で行う。

## 10. 実装で変えた点

- **選択中の印はチェック記号にした。** `IsCheckable` / `IsChecked` を使う案だったが、
  このアプリのメニューは独自のテンプレートで描いていて、印を出す欄が無い。
  行末に `✓` を出す形にした（同じ理由で、既存の「滑らかにする」の印も出ていない）。
- 色の解決は `Services/ColorPalette.cs` に置いた。設計では `ThemeManager` に足す案だったが、
  濃くする・薄くするの作り置きも要るので、配色そのものの入れ替えとは分けた。
- 描くときの色 id は `ColorPalette.Effective` を通す。知らない色をここで `null` に倒すので、
  「知らない色は既定色で描く」がリソースの引き方に依存しなくなる。
- ブロックの接続点（四辺の丸）は `HeaderFill` と `BorderBrush` を使い回しているため、
  設計のとおり囲みの色と一緒に染まる。
- **Undo は 1 回の選択ごとに積む。** 設計では文字入力と同じ 2 秒の集約に乗せる案だったが、
  それだと赤→青→緑と続けて試したあとの `Ctrl+Z` が青ではなく既定まで戻ってしまう。
  色選びは離散的な操作なので、まとめない。
- **色見本は彩度のある枠の色で描く。** 見出しの下地（`Block.Header.Fill.<id>`）は
  どれもほぼ白で、13 px の見本では 9 色が見分けられなかった。実際の囲みの見え方より、
  選ぶときの見分けやすさを優先した。
- **集約された線は色を選べない。** 4.1 に書いたとおり、重なって見えないため。
- `Block.Header.Fill.slate` を既定より少し冷たい色にした。同じ値だと、灰を選んでも
  見出しが既定と区別できなかった。

## 11. 決めていないこと

- 灰（`slate`）と既定の見分けが実画面で付くか。付かなければ `slate` を落として 8 色にする。
- 大量に色を付けたときの印象。うるさければ `Block.Fill` の不透明度を下げる。
- ミニマップでは色付きの囲みだけ `Block.Stroke.<id>` を使うので、既定色の囲みより強く出る。
  地図の上でうるさければ、薄めた色を使う。
